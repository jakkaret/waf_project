3.1 ปัญหา Data Leakage ใน Pipeline เดิม และการค้นพบเชิงลึก

จากการตรวจสอบโค้ด Pipeline เดิม พบว่ามีการนำ Payload เสริม 37 รายการมาทำ df_combined = pd.concat([df_csic] + [df_benign_extra]*500 + [df_attack_extra]*500) ซึ่งการคูณข้อมูลซ้ำ 500 เท่าก่อนทำ train_test_split(75/25) ทำให้แถวข้อมูลที่เหมือนกันทุกตัวอักษร 375 แถวไปอยู่ใน Train Set และอีก 125 แถวหลุดไปอยู่ใน Test Set ส่งผลให้โมเดลทำคะแนนได้ Accuracy สูงเกินจริง (Fake 94%+) จากการท่องจำตัวอย่างเดิม (Overfitting & Memorization)

❌ ปัญหาของ Pipeline และ CSIC 2010 เดิม

  • Exact Row Duplication คูณ 500 เท่า ทำให้เกิด Data Leakage รุนแรง
  • CSIC มี Header Label Noise กว่า 5,400 แถวที่เป็น URL ว่างแต่โดนติดป้าย Attack
  • Path-Length Bias: URL สั้นถูกมองเป็น Attack เพราะ CSIC มีแต่ e-commerce ยาวๆ
  • ขาด Threat Vectors ยุคใหม่ (SSRF, SSTI, NoSQL, Log4Shell)

✅ วิธีการแก้ไขด้วย Synthetic Data Generator

  • พัฒนาสคริปต์สังเคราะห์ข้อมูลอัจฉริยะใน ml/download_dataset.py 35,000+ ตัวอย่าง
  • Mutation Engine: Fuzzing, URL Encoding (%2527, %27), Comment Evasion (/**/)
  • Global SHA-256 Deduplication การันตีข้อมูล 60,106 แถวไม่ซ้ำกัน 100% (Zero Leakage)
  • ทดสอบบน Holdout Unseen Test Data 15,027 แถวจริง

5. Layer 1: ModSecurity CRS v4.0 & Blast Radius Simulator

Anomaly Scoring Model vs Traditional WAF

ในระบบนี้เราใช้ OWASP CRS Anomaly Scoring Mode (Threshold = 10) โดยแต่ละ Rule ที่ตรวจพบจะบวกคะแนนความเสี่ยง (Anomaly Score) เข้าตัวแปร tx.inbound_anomaly_score และจะบล็อก 403 Forbidden ที่ Phase 2 ทันทีเมื่อคะแนนรวมถึงเกณฑ์ ช่วยลด False Positive ได้อย่างดีเยี่ยมเมื่อเทียบกับการบล็อกแบบ Rule-by-Rule

Score = Critical(5) + High(4) + Medium(3) + Low(2)
Block Action: tx.inbound_anomaly_score >= 10

Q1 ทำไม Accuracy 80.5% ถึงดีกว่า 94% เดิม?

ตอบ: ตัวเลข 94% เดิมเกิดจาก Data Leakage ที่มีการคูณข้อมูลซ้ำ 500 เท่า ทำให้ Test Set ซ้ำกับ Train Set (โมเดลท่องจำตัวอย่างเดิม) ส่วน 80.5% นี้เป็นการทดสอบบน Unseen Holdout Test Data ที่ไม่ซ้ำกัน 100% และมี Benign Recall สูงถึง 98.97% (False Alarm เพียง 1.03%) ซึ่งเป็นตัวเลขที่สะท้อนประสิทธิภาพจริงและใช้งานได้ในระบบ Production โดยไม่บล็อกผู้ใช้ทั่วไป

Q2 ทำไมจึงต้องใช้ทั้ง Random Forest และ Isolation Forest ร่วมกัน?

ตอบ: Random Forest (Supervised) ให้ความแม่นยำสูงมากกับ Known Attack Patterns ที่มี Signature ชัดเจน (เช่น SQLi, XSS) ส่วน Isolation Forest (Unsupervised) จะเรียนรู้เฉพาะ Normal Traffic Distribution เพื่อช่วยตรวจจับพฤติกรรมผิดปกติที่ไม่เคยพบมาก่อน (Zero-Day Anomaly Detection) การผสานแบบ Ensemble จึงครอบคลุมภัยคุกคามได้สมบูรณ์แบบ

Q3 ทำไม ML ไม่นำไปขวางทราฟฟิกตรงๆ (In-line) แต่ทำเป็น Microservice?

ตอบ: เพื่อรักษา High Throughput และ Low Latency (< 2ms) ของ Edge WAF โดยให้ ModSecurity CRS ตรวจจับแบบเร็วใน In-line Fast Path และส่ง Request ผ่าน Stream Logging / Async Microservice ให้ ML วิเคราะห์เชิงลึกและสร้างกฎใหม่ (Auto Rule Generation) โดยไม่ทำให้ Server และผู้ใช้งานต้องรอโมเดลประมวลผล

Q4 ถ้ามี Attack Payload ยาวมากหรือผ่าน Encoding มา ML จะตรวจจับได้อย่างไร?

ตอบ: ระบบทำ Double URL Decoding ก่อนส่งเข้า Feature Extractor เสมอ และมีฟีเจอร์ตรวจจับ Entropy, Special Character Ratio, และความยาวผิดปกติ (is_oversized_payload) ทำให้ตรวจจับเทคนิค Evasion และ Obfuscation ได้ครบถ้วน
