วิเคราะห์ระบบ WAF + CDN ต้นน้ำถึงปลายน้ำ

ถอดรหัสการทำงานจริงของระบบป้องกันเว็บไซต์ WAF (Web Application Firewall) และเครือข่าย CDN กระจายทราฟฟิก เจาะลึก 4 หน้าจอหลักพร้อม Interactive Mockup จำลองบทบาทผู้ใช้งานจริง และตรวจสอบสิ่งที่เกิดขึ้นเบื้องหลังในระดับ Kernel, Network, WAF Engine และ Database

TLS & Rate Limit

📖 คำอธิบายเชิงลึก 4 ระบบหลัก (Purpose, Visuals, Under-the-hood & Tools)

รายละเอียดการทำงาน กลไกเบื้องหลัง และเครื่องมือที่ใช้ในแต่ละโมดูลของระบบ

1. Security Dashboard (ภาพรวมความปลอดภัย)
Frontend + Fast Analytics

📌 มีไว้ทำไม & ดูอะไรได้บ้าง

  • วัตถุประสงค์: เป็นศูนย์รวมการสังเกตการณ์ (Single Pane of Glass) ให้ผู้ดูแลระบบและผู้ใช้งานเห็นสถานะความปลอดภัยแบบ Real-time
  • Total Events / Blocked Rate: ติดตามปริมาณทราฟฟิกและเปอร์เซ็นต์ภัยคุกคามที่ถูกสกัดกั้น
  • Attack Vector Breakdown: แยกประเภทการโจมตี (SQLi, XSS, RCE, Flood) ตามกฎ OWASP ModSecurity Core Rule Set
  • AI / Automated Summary: สรุปพฤติกรรมของ IP อันตรายและข้อแนะนำการตั้งค่าความปลอดภัย

⚙️ เบื้องหลังทำงานยังไง & สแตกที่ใช้

  • Data Pipeline: React Frontend โพลลิ่ง GET /api/analytics/stats ทุก 10 วินาทีผ่าน TanStack Query
  • Analytics Engine: Backend ยิง SQL Aggregate เข้า ClickHouse MergeTree ซึ่งประมวลผลข้อมูลนับล้านแถวได้ในเวลา <10ms
  • Stack: FastAPI (Python 3.11), ClickHouse 23+, Redis 7 (Cache), Recharts (Data Visualizer), TailwindCSS
2. Traffic Log (บันทึกทราฟฟิกและประวัติการโจมตี)
Audit & Forensics

📌 มีไว้ทำไม & ดูอะไรได้บ้าง

  • วัตถุประสงค์: ใช้สำหรับสืบสวนเชิงลึก (Forensic Analysis) เมื่อเกิดเหตุการณ์โจมตี หรือตรวจสอบ False Positive (คำขอปกติที่โดนบล็อกผิดพลาด)
  • ข้อมูลที่แสดง: วันเวลา (Timestamp), IP ต้นทาง, Geo Location, HTTP Method, Requested URL/Payload, Status Code (200, 403, 429), และ ModSecurity Rule ID
  • CSV Export: ดาวน์โหลดบันทึกเพื่อนำไปทำรายงานความปลอดภัยหรือส่งให้ฝ่ายกฎหมาย/SOC

⚙️ เบื้องหลังทำงานยังไง & สแตกที่ใช้

  • Inspection & Logging: เมื่อ Request ผ่าน Nginx WAF ตัว ModSecurity จะตรวจคำขอใน Phase 1 (Headers) และ Phase 2 (Body)
  • Audit Shipping: หากมีคะแนน Anomaly Score > 10 จะเขียน Log ลง /var/log/modsecurity/audit.log จากนั้น Python Log Forwarder จะส่งแบบ Streaming เข้า ClickHouse ตาราง security_audit_logs
  • Stack: ModSecurity CRS 3.3/4.0, Nginx log_format, Python Async Ingestion, ClickHouse DB
3. Web Origin & Tunnel (จัดการเซิร์ฟเวอร์และทันเนล)
Routing & DNS

📌 มีไว้ทำไม & ดูอะไรได้บ้าง

  • วัตถุประสงค์: ให้ลูกค้าสามารถเพิ่มเว็บไซต์/แอปพลิเคชัน (Origin) เข้ามาผูกกับเครือข่าย WAF Proxy โดยไม่ต้องย้ายโฮสติ้งเดิม
  • Quota Management: กำหนดจำนวน Origin สูงสุดที่อนุญาตต่อบัญชี (เช่น 5 Origins) เพื่อควบคุมทรัพยากร
  • DNS Setup Wizard: แสดงค่า CNAME และ TXT Verification Token ให้ลูกค้านำไปใส่ที่ DNS ผู้ให้บริการ (Cloudflare, Namecheap)

⚙️ เบื้องหลังทำงานยังไง & สแตกที่ใช้

  • Origin Storage: จัดเก็บข้อมูล Domain และ Target IP/Port ใน AWS DynamoDB / LocalStack
  • DNS Background Verification: Worker (dns_verification_worker.py) ใช้ dnspython เช็กสถานะการชี้ DNS ในอินเทอร์เน็ต เมื่อถูกต้องจะเปลี่ยนสถานะเป็น Active
  • Reverse Proxy Upstream: Nginx/Caddy สลับ Upstream ไปยัง Origin IP ผ่าน SSL Tunneling
  • Stack: AWS DynamoDB, FastAPI Backend, Python dnspython, Caddy 2 SSL Auto-provisioning
4. CDN & Edge Node (เครือข่าย Edge Caching)
Edge Performance & Sync

📌 มีไว้ทำไม & ดูอะไรได้บ้าง

  • วัตถุประสงค์: วางเซิร์ฟเวอร์ไว้ตามภูมิภาคต่างๆ (เช่น SG: 45.154.26.91, TH: 178.104.53.123) เพื่อลด Latency แคชข้อมูล Static และสกัดกั้นการโจมตีตั้งแต่ขอบเครือข่ายก่อนถึงเซิร์ฟเวอร์หลัก
  • Cache Ratio (HIT/MISS/BYPASS): ตรวจดูอัตราการตอบสนองจากหน่วยความจำแคช
  • Edge Health & Rule Status: ตรวจสอบว่าโหนดแต่ละตัวซิงก์กฎความปลอดภัยล่าสุดแล้วหรือไม่

⚙️ เบื้องหลังทำงานยังไง & สแตกที่ใช้

  • Daemon Rule Synchronization: สคริปต์ 99-rulesync.sh บน Edge Node จะส่งคำขอเช็ก Checksum Bundle ไปที่ Control API (178.104.53.123:8070) ทุก 5 วินาที
  • Zero-Downtime Reload: หากพบลักษณะกฎใหม่ จะโหลด Tarball แตกไฟล์ลง /opt/custom-rules รัน nginx -t เพื่อทดสอบความถูกต้อง แล้วสั่ง nginx -s reload ทันทีโดยไม่สะดุดการทำงาน
  • Caching Engine: proxy_cache_path /var/cache/nginx พร้อมระบบ Purge ผ่าน REST API
  • Stack: Nginx HTTP Cache, ModSecurity Daemon, Docker Compose, GeoDNS, Bash Sync Loop

Roleplay Simulation: สวมบทบาทผู้ใช้จริง vs แฮกเกอร์

จำลองสิ่งที่เกิดขึ้นจริงในมุมมองหน้าบ้าน (Frontend Action) และสิ่งที่ระบบหลังบ้าน (Backend & Edge Execution) ทำงานตอบสนองแบบ Step-by-Step

Scenario A: เจ้าของเว็บเพิ่ม Origin และตั้งค่าโดเมน
1
ผู้ใช้กดเพิ่ม Origin: กรอกชื่อ My Shop, IP 178.104.53.123, Port 8080 บนหน้าเว็บ
2
ระบบหลังบ้านบันทึก: FastAPI ตรวจสอบรูปแบบ IP และเช็กโควตา จากนั้นบันทึกข้อมูลลง DynamoDB origins table
3
ผู้ใช้ผูกโดเมน & ชี้ DNS: นำค่า CNAME ไปตั้งใน Cloudflare ให้ชี้มาที่ Edge IP 45.154.26.91
4
Worker ตรวจสอบสำเร็จ: dns_verification_worker.py ดึง Record พบค่าถูกต้อง อัปเดตสถานะเป็น Active พร้อมสร้างใบรับรอง SSL อัตโนมัติ
Scenario B: แฮกเกอร์ยิง SQL Injection เข้ามา
1
แฮกเกอร์ส่ง Payload: ยิงคำขอ GET /dvwa/vulnerabilities/sqli/?id=1'+OR+'1'='1 มาที่โดเมน
2
Edge Node สกัดกั้น: ModSecurity ตรวจพบ CRS Rule 942100 คำนวณ Anomaly Score แตะ 15 คะแนน (เกินเกณฑ์ 10)
3
ตัดการเชื่อมต่อทันที: Edge Nginx ตอบกลับหน้า 403 Forbidden ทันที โดยที่ Request นี้ไม่ได้วิ่งไปถึง Main Server แม้แต่น้อย
4
Log & Alert อัตโนมัติ: Log ถูกส่งเข้า ClickHouse หน้า Dashboard อัปเดตกราฟทันที และ Telegram Bot ส่งแจ้งเตือนแอดมิน

บทสรุปการประเมินสถาปัตยกรรม (Architectural Scrutiny Verdict)

สถาปัตยกรรมของระบบ WAF & CDN นี้ถูกออกแบบตามมาตรฐาน Edge-First Security Architecture อย่างถูกต้อง: การแยก Control Plane (FastAPI + DynamoDB บน Main) ออกจาก Data Plane (Nginx + ModSecurity CRS บน Edge Node) ทำให้ระบบมีเสถียรภาพสูง ทนต่อการถูกโจมตีแบบ DDoS และช่วยลดโหลดของ Main Origin ได้อย่างมีนัยสำคัญ
